# 재시도 운영 가이드 문서 설계 동결 — BF-1400 / BF-1402

- 상태: active (planner freeze)
- 대상 문서: `docs/operator/retry-guide.md`
- 실행 담당: developer (BF-1401)
- 검증 담당: tester (BF-1404)
- 본 문서: `docs/plans/retry-guide-plan-BF-1400.md` (planner 실행 설계)

이 문서는 PM 분해를 developer가 그대로 따를 수 있도록 `docs/operator/retry-guide.md`에
추가할 섹션 구조, 한·영 병행 규칙, 보존 범위, 검증 기준을 실행 설계로 동결한다.
developer는 여기서 동결한 섹션 구조와 보존 범위를 변경하지 않는다.

---

## 1. 목적 및 배경 (Objective)

운영자가 재시도(retry) 판단을 문서 하나만으로 일관되게 내릴 수 있도록,
재시도 운영 가이드에 **판단에 필요한 4개 신규 섹션**을 추가한다.
본 planner 산출물은 그 4개 섹션의 제목·순서·형식·보존 범위·검증 기준을 동결하며,
developer는 아래 계약을 그대로 구현한다.

### 1.1 사용자 시나리오 (User scenario)

- 운영자는 실패한 작업을 마주하면 `docs/operator/retry-guide.md`를 연다.
- **목적** 섹션에서 이 가이드가 무엇을 판단시키는지 확인한다.
- **재시도 가능 조건** 섹션에서 현재 실패가 재시도 대상인지 판별한다.
- **확인 체크리스트** 섹션의 항목을 순서대로 밟아 사전 조건을 확인한다.
- **실패 시 중단 조건** 섹션에서 재시도를 멈추고 에스컬레이션할 시점을 판단한다.

---

## 2. 문서 섹션 구조 계약 (동결)

developer는 아래 4개 섹션을 **아래 제목·순서 그대로** `docs/operator/retry-guide.md`에 추가한다.
각 섹션 제목은 `한국어/English` 병행 형식을 사용하며, 아래 헤딩 텍스트를 문자 그대로 사용한다.

| 순서 | markdown 헤딩 (문자 그대로) | 역할 |
|------|----------------------------|------|
| 1 | `## 목적 / Purpose` | 가이드가 무엇을 판단시키는지 |
| 2 | `## 재시도 가능 조건 / Retryable conditions` | 재시도 대상 판별 기준 |
| 3 | `## 확인 체크리스트 / Verification checklist` | 재시도 전 확인 절차 |
| 4 | `## 실패 시 중단 조건 / Stop conditions` | 재시도 중단·에스컬레이션 기준 |

### 2.1 한·영 병행 형식 규칙 (동결)

- **헤딩**: `## <한국어> / <English>` 형식. 슬래시 양옆 공백 1칸씩.
- **본문**: 각 문단·리스트 항목은 한국어 문장을 먼저 쓰고, 바로 다음 줄에 영어 대응 문장을 쓴다.
  - 한국어 줄과 영어 줄은 **의미가 1:1 대응**해야 한다(한쪽에만 있는 정보 금지).
- **리스트**: 한국어 항목과 영어 항목을 개별 bullet로 나란히 둔다.
  - 예: `- 네트워크 일시 오류는 재시도 가능하다.` / `- Transient network errors are retryable.`
- 4개 섹션 모두 최소 1개의 한국어 문장과 그에 대응하는 영어 문장을 포함한다.

### 2.2 섹션별 내용 계약

각 섹션의 **필수 포함 요소**만 규정하며, 구체 문구는 developer가 위 형식 규칙 안에서 작성한다.

1. **목적 / Purpose**
   - 이 가이드의 사용 목적(운영자의 재시도 판단 지원)을 1~2문장으로 한·영 병행 기술.
2. **재시도 가능 조건 / Retryable conditions**
   - 재시도 가능한 실패 유형을 한·영 병행 리스트로 나열(최소 2개 항목).
   - 예: 일시적 네트워크 오류, 타임아웃 등(구체 목록은 developer 판단, 미검증 외부 사실 금지).
3. **확인 체크리스트 / Verification checklist**
   - 재시도 전에 확인할 항목을 **순서 있는(ordered) 또는 체크박스** 리스트로 한·영 병행 기술(최소 2개 항목).
4. **실패 시 중단 조건 / Stop conditions**
   - 재시도를 멈추고 에스컬레이션해야 하는 조건을 한·영 병행 리스트로 기술(최소 2개 항목).

## 3. 보존 범위 (Preservation scope — 동결)

developer는 아래 보존 범위를 반드시 지킨다.

### 3.1 변경 금지 (MUST NOT)

- **기존 섹션 미변경**: `docs/operator/retry-guide.md`에 이미 존재하는 섹션·문단·헤딩을 수정·삭제·재배치하지 않는다.
  신규 4개 섹션은 **추가(append)만** 한다.
- **README 미변경**: 프로젝트 `README` 및 다른 문서를 이번 작업에서 수정하지 않는다.
- **소스 코드 미변경**: 어떤 소스 코드·설정·workflow 파일도 변경하지 않는다. 순수 문서 작업이다.

### 3.2 내용 금지 (MUST NOT include)

- **미검증 명령 금지**: 실행 가능 여부를 확인하지 않은 CLI/셸 명령을 문서에 넣지 않는다.
  코드 블록에는 형식 예시로만 명령을 두되, 임의 실행 결과를 사실처럼 단정하지 않는다.
- **외부 링크 금지**: 외부 URL(`http://`, `https://` 등 저장소 밖 링크)을 삽입하지 않는다.
  참조가 필요하면 저장소 내 상대 경로만 사용한다.

## 4. Acceptance Criteria (Given/When/Then)

### AC-1 — 4개 신규 섹션의 제목·순서·형식
- **Given** developer가 `docs/operator/retry-guide.md`를 편집할 때
- **When** 신규 섹션을 추가하면
- **Then** §2 표의 4개 헤딩이 **정확한 문자·순서**로 존재하고, 각 섹션이 §2.1 한·영 병행 형식을 만족한다.

### AC-2 — 보존 범위 준수
- **Given** developer의 변경이 완료되었을 때
- **When** diff를 확인하면
- **Then** 기존 섹션·README·소스 코드는 변경되지 않았고, 미검증 명령·외부 링크가 새로 추가되지 않았다(§3).

### AC-3 — 렌더·링크·코드 블록 검증 통과
- **Given** 변경된 문서가 존재할 때
- **When** markdown 렌더·링크·코드 블록 검증(§5)을 실행하면
- **Then** 렌더 오류가 없고, 모든 링크가 유효(저장소 내 상대 경로)하며, 모든 코드 블록의 fence가 정상 종료된다.

---

## 5. 검증 기준 (Verification — 완료 조건)

tester(BF-1404)와 developer의 self-check가 공유하는 완료 조건이다.

1. **markdown 렌더 검증**: 문서가 렌더 오류 없이 파싱된다.
   - 모든 헤딩 레벨이 유효하고, §2 표의 4개 헤딩이 정확한 텍스트로 존재한다.
2. **링크 검증**: 문서 내 모든 링크가 유효하다.
   - 외부 URL이 없고(§3.2), 상대 경로 링크는 저장소 내 실제 파일을 가리킨다.
3. **코드 블록 검증**: 모든 코드 블록의 여는/닫는 fence(```` ``` ````)가 짝을 이루어 종료된다.
   - fence가 열린 채 끝나는 블록이 없다.
4. **테스트**: `tests/retry-guide.test.js`(tester 소유)가 위 3개 기준을 자동 검증하며 통과한다.
   - 테스트는 focused scope로 실행하고, 무관 module 회귀는 실행하지 않는다.

### 5.1 검증 명령 (참고)

- 정적 검증은 `tests/retry-guide.test.js`가 담당한다. 본 planner 문서는 명령을 단정하지 않으며,
  실행 authority는 tester packet이 정의한다(focused scope, `BRIX_TEST_SCOPE=focused`).

## 6. Edge case · 실패 케이스

- **기존 문서가 없을 때**: `docs/operator/retry-guide.md`가 아직 없으면 developer가 신규 생성하고
  4개 섹션을 §2 순서대로 작성한다. operator 디렉터리도 함께 생성한다.
- **기존 섹션과 헤딩 충돌**: 동일 헤딩이 이미 있으면 중복 추가하지 말고 기존 섹션을 보존한 채
  planner에게 diff 기준으로 확인을 요청한다(임의 병합 금지).
- **한·영 불일치**: 한국어 줄과 영어 줄의 의미가 어긋나면 렌더는 통과해도 AC-1 위반이다.
- **코드 블록 내 명령**: 예시 명령을 코드 블록에 둘 수는 있으나, 실행 결과를 사실로 단정하면 §3.2 위반이다.
- **외부 링크 유입**: 참조 목적이라도 외부 URL은 금지. 저장소 내 상대 경로로 대체한다.

- **reviewer**: §3 보존 범위 위반(기존 섹션/README/소스 변경, 미검증 명령, 외부 링크)과 §2 형식 준수를 review verdict로 확인.
- **tester (BF-1404)**: §5 검증 기준을 `tests/retry-guide.test.js`로 자동 검증.
