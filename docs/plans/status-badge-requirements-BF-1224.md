# 운영 상태 배지 요구사항 정의 (BF-1224 / 작업 BF-1225)

- 문서 유형: 기획 산출물 (planning-contract@v1)
- 작성 페르소나: planner (박기획)
- 실행 범위: document-only — 본 문서는 코드 변경 산출물을 포함하지 않는다.
- 검증 주체: reviewer 는 본 문서를 수용 기준 판정 기준으로 삼는다.

---

## 1. 목적 (Purpose)

운영자가 서비스의 현재 상태와 **필요한 조치를 한눈에** 이해할 수 있도록, 운영 화면 상단에 단일 "운영 상태 배지(status badge)"를 노출한다.

배지가 해결하려는 문제:

- 운영자가 여러 지표를 개별 확인하지 않고도 서비스가 정상인지/주의가 필요한지/즉시 대응이 필요한지를 즉시 판단하게 한다.
- 각 상태가 요구하는 **운영자 행동**을 상태와 함께 명확히 전달하여, 판단과 조치 사이의 지연을 줄인다.

비목표 (Non-goals):

- 상태 산출 알고리즘(임계값 계산·집계 로직)의 구현 세부는 본 문서 범위 밖이다. 본 문서는 **상태 모델과 의미, 행동 지침, 수용 기준**만 확정한다.
- 디자인 시안(색상·타이포·레이아웃 픽셀 스펙)은 designer 영역이다. 본 문서는 상태별 의미 구분만 규정한다.

---

## 2. 상태 모델 (State Model)

배지는 상호 배타적인 **세 가지 상태** 중 정확히 하나를 표시한다. 상태는 심각도 오름차순으로 정의한다.

| 상태 | 의미 (운영자에게 전달되는 뜻) |
| --- | --- |
| `healthy` | 서비스가 정상 동작 중이며 운영자 개입이 필요하지 않다. 핵심 기능이 모두 정상 응답하고 있음을 뜻한다. |
| `degraded` | 서비스가 동작하지만 일부 기능·성능이 저하되었거나 경고 신호가 감지된 상태다. 즉각적인 장애는 아니나 **주의 관찰과 예방 조치**가 필요함을 뜻한다. |
| `unavailable` | 서비스의 핵심 기능이 사용 불가하거나 응답하지 않는 상태다. 사용자 영향이 발생 중이며 **즉시 대응**이 필요함을 뜻한다. |

상태 모델 규칙:

- 배지는 위 세 상태 중 하나만 표시하며, 동시에 둘 이상을 표시하지 않는다.
- 상태 값이 산출되지 않거나 알 수 없는 경우에도 세 상태 외의 임의 값을 노출하지 않는다. 산출 실패는 심각도가 가장 높은 방향(가장 안전한 해석)인 `unavailable` 로 표시한다. (아래 6장 edge case 참조)

---

## 3. 상태별 운영자 행동 지침 (Operator Actions per State)

각 상태는 대응하는 운영자 행동 지침을 **상태별로 1:1** 로 갖는다.

### 3.1 `healthy`
- 별도 조치 불필요. 정기 모니터링을 유지한다.
- 최근 `degraded`/`unavailable` 에서 복구된 직후라면 회복이 안정적으로 유지되는지 짧게 관찰한다.

### 3.2 `degraded`
- 저하가 감지된 대상(기능/의존 구성요소)을 확인하고 영향 범위를 파악한다.
- 사용자 영향이 확산되는지 지표 추세를 관찰하고, 필요 시 예방적 완화 조치(재시도·용량 조정·트래픽 조절 등)를 준비한다.
- 상태가 `unavailable` 로 악화될 조짐이 있으면 대응 담당자에게 사전 공유한다.

### 3.3 `unavailable`
- 즉시 장애 대응을 개시한다. 영향받는 핵심 기능과 사용자 범위를 확인한다.
- 사전 정의된 인시던트 대응 절차(에스컬레이션·공지)를 따른다.
- 복구 조치를 적용하고, 배지가 `degraded` 또는 `healthy` 로 회복되는지 확인한다.

---

## 4. 수용 기준 (Acceptance Criteria, Given/When/Then)

검증 가능한 형태로 기술한다. reviewer 는 아래 각 항목의 충족 여부로 판정한다.

### AC-1. 세 상태의 의미가 각각 정의된다
- Given 본 요구사항 문서를 읽는 이해관계자가
- When `healthy`, `degraded`, `unavailable` 각 상태 항목을 확인하면
- Then 세 상태 각각에 대해 서로 구분되는 의미가 명시되어 있다. (2장 표)

### AC-2. 각 상태에 대응하는 운영자 행동 지침이 상태별로 명시된다
- Given 세 상태가 정의된 상태에서
- When 운영자가 특정 상태를 마주하면
- Then 해당 상태에 대응하는 운영자 행동 지침이 상태별로 존재하며 서로 구분된다. (3.1 / 3.2 / 3.3)

### AC-3. 목적과 수용 기준이 검증 가능하게 기술되며 코드 변경 산출물을 포함하지 않는다
- Given 본 문서가 기획 산출물로 제출된 상태에서
- When reviewer 가 문서를 검토하면
- Then 배지의 목적(1장)과 수용 기준(4장)이 검증 가능한 형태로 서술되어 있고, 본 산출물에 코드 변경(소스/구현 파일)이 포함되어 있지 않다.

---

## 5. 표시 요구사항 (Display Requirements)

- 배지는 상태 값과 함께, 해당 상태의 운영자 행동을 인지할 수 있는 정보(상태 라벨 및 3장 지침으로 연결되는 단서)를 제공한다.
- 상태 라벨 텍스트는 세 상태를 언어적으로 구분할 수 있어야 하며, 색상만으로 상태를 구분하도록 강제하지 않는다(접근성 고려).
- 구체적 색상·아이콘·레이아웃은 designer 가 확정한다. 본 문서는 "세 상태가 시각적·언어적으로 구분되어야 한다"는 제약만 규정한다.

---

## 6. Edge case · 실패 케이스

| 케이스 | 요구되는 동작 |
| --- | --- |
| 상태 값 산출 실패 / 알 수 없음 | 임의의 네 번째 상태를 만들지 않고, 가장 안전한 해석인 `unavailable` 로 표시한다(즉시 확인 유도). |
| 상태 데이터가 오래됨(stale) | 최신 상태를 신뢰할 수 없으므로 최소 `degraded` 이상으로 표시하거나, 데이터가 오래되었음을 함께 알린다. |
| 상태 간 잦은 진동(flapping) | 짧은 시간 내 상태가 반복 전환되면 운영자 피로를 유발하므로, 표시 안정화(완화) 필요성을 후속 구현에서 고려한다. (임계값·완화 로직은 본 문서 범위 밖, 요구사항으로만 명시) |
| 세 상태 외 값 유입 | 정의된 세 상태 외 값은 노출하지 않는다. |

---

## 7. 데이터 모델 (개념 수준)

본 문서는 구현 스키마를 확정하지 않으며, 상태 표현에 필요한 개념 필드만 제시한다.

- `status`: `healthy | degraded | unavailable` 중 하나 (필수)
- `observedAt`: 상태가 산출된 시점 (stale 판정 및 표시에 사용)

실제 API 스펙·저장 스키마·산출 로직은 후속 developer/designer 작업에서 본 요구사항을 근거로 확정한다.
